## 질문과 배경

- 기간: 2026.04 ~ 2026.06 (클라우드 컴퓨팅 수업 11조)
- 팀: 3인. 나는 팀장이자 Flutter 프론트엔드를 맡았고, 한 명은 백엔드와 프론트엔드를, 다른 한 명은 백엔드와 AWS를 맡았다.
- 기술: Flutter, Dart, Spring Boot, PostgreSQL, Google OAuth 2.0, JWT, AWS EC2·RDS·S3
- 코드: [Ddaom-frontend](https://github.com/Ddaom-team/Ddaom-frontend), [Ddaom-backend](https://github.com/Ddaom-team/Ddaom-backend)

출발점은 두 가지 불편이었다. 하나는 핫플레이스에 가도 어디가 포토존인지 찾기 어렵다는 것이고, 다른 하나는 같은 자리에서 찍어도 내 사진만 이른바 '밤티'로 나온다는 것이다. 그래서 잘 나온 사진의 자세와 구도를 카메라 화면 위에 겹쳐서 보여 주는 앱을 만들기로 했다.

처음 목표는 기능을 완성하는 것이었다. 그런데 개발하는 도중에 앱 코드 안에 외부 API 자격증명이 그대로 들어 있다는 사실을 발견했다. 그때부터 "기능을 만드는 사람이 보안 문제를 어디까지 직접 막을 수 있는가"가 이 프로젝트에서 가장 큰 질문이 됐다.

## 앱의 흐름

사용자 흐름은 단순하다. 지도에서 핫플레이스를 고르고, '따오기' 버튼을 누르면 가이드 카메라가 열린다.

- **장소 등록**: 네이버 지도 검색 결과로 장소를 등록한다. 주소와 좌표를 손으로 넣지 않아도 된다.
- **포토존 단위**: 같은 장소 안에서도 찍는 자리가 여러 곳이다. 예를 들어 인경호는 정면과 정자가 다른 포토존이다. 그래서 장소 아래에 포토존을 따로 두었다.
- **업로드**: 사진을 올릴 때 테마와 사진 유형(인물/풍경)을 지정한다. 여러 장을 연속으로 찍은 뒤 고른 사진만 한 번에 올릴 수 있다.
- **커뮤니티**: 팔로우 피드, 인기 피드, 북마크, 마이페이지를 만들었다.

## 포즈 가이드는 어떻게 동작하나

포즈 가이드는 Google ML Kit Pose Detection을 썼다. 사진 한 장에서 사람 몸의 랜드마크 33개를 뽑아 준다. 이 작업이 기기 안에서 끝나기 때문에 서버를 오가는 지연이 없고, 사진을 외부로 보내지 않아 프라이버시에도 유리하다.

1. 참고 사진에서 랜드마크를 뽑아 0~1 사이 값으로 정규화한다. 사진 크기가 달라도 비교할 수 있게 하기 위해서다.
2. 카메라 화면에서도 실시간으로 내 랜드마크를 뽑는다.
3. 참고 자세는 흰색, 내 자세는 분홍색으로 겹쳐 그린다. 사용자는 분홍 선을 흰 선에 맞추면 된다.

여기에 세 가지를 보완했다.

- **상반신 사진**: 정규화한 좌표가 0~1 밖이면 화면 밖에 있는 부위로 보고 그리지 않는다(`inFrame`). 그래서 상반신만 찍힌 사진이면 보이는 부위만 가이드로 나온다.
- **떨림 줄이기**: 실시간으로 뽑은 내 자세가 프레임마다 흔들려서, 이전 값과 섞는 지수이동평균(EMA)을 적용했다.
- **풍경 사진**: 사람이 없는 사진은 랜드마크 대신 원본 사진을 반투명하게 겹쳐 구도를 맞추게 했다.

## 확인 과정

> **주의** 모바일 앱에 넣은 키는 누구나 앱을 풀어서 꺼낼 수 있다. 앱 안에 있는 값은 비밀이 아니라고 가정해야 한다.

### 1. 앱 안의 자격증명을 서버로 옮겼다

앱 코드에 네이버 검색 Client ID와 Secret이 하드코딩되어 있었고, 앱이 외부 API를 직접 호출하고 있었다. 검색, 이미지, 지오코딩 호출을 모두 백엔드 프록시로 옮겼다. 이제 앱은 검색어를 보내고 결과만 받는다. 자격증명은 서버 환경변수로만 주입하고, 노출됐던 옛 키는 폐기했다.

같은 이유로 네이버 지도 설정 파일(`naver_map_config.dart`)은 `.gitignore`에 넣었다. 홈 디렉터리 전체가 저장소로 잡혀 있는 환경이라 `git add .`도 쓰지 않기로 했다.

### 2. 백엔드 경계를 다시 봤다

프록시를 만들고 나니 서버 쪽 경계도 다시 보였다. 아래 네 가지를 고쳐 EC2에 배포했다.

| 보완        | 막으려는 위협                                 | 내용                                                                                                                                                                                                  |
| ----------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CORS        | 다른 사이트가 사용자 권한으로 API를 부르는 것 | 와일드카드와 credentials 반사를 막았다. JWT를 헤더로 보내는 방식이라 `allowCredentials(false)`로 충분했다.                                                                                            |
| 업로드 검사 | 이미지로 위장한 스크립트 업로드               | 확장자가 아니라 파일 앞 12바이트(매직 바이트)로 JPEG, PNG, GIF, BMP, WEBP, HEIC만 허용했다. SVG는 안에 스크립트를 넣을 수 있어서 거부했다. iOS 기본 사진 형식인 HEIC가 막히지 않는지도 따로 확인했다. |
| 호출 제한   | 네이버 API 쿼터 소진과 요금 폭탄              | 프록시에 고정 윈도우 방식으로 이메일(로그인 전에는 IP) 기준으로 분당 60회 제한을 걸고, 넘으면 429를 돌려준다.                                                                                                       |
| 닉네임 검증 | DB 컬럼 초과와 비정상 입력                    | 길이(20자)와 형식을 서버에서 검증했다.                                                                                                                                                                |

### 3. 레거시 공격을 직접 시도했다

새로 고친 부분 말고, 원래 있던 코드도 흔한 공격으로 확인했다.

- **SQL 인젝션**: JPA 파라미터 바인딩을 쓰고 있어서 막혀 있었다.
- **JWT 위조**: 서명과 만료를 검증하고, 512비트 키를 쓴다. 키가 비어 있으면 서버가 아예 부팅되지 않게 되어 있었다.
- **경로 조작**: 업로드 경로를 만드는 `normalizeDirectory()`가 `..`을 차단하고 있었다.
- **SSRF**: 직접 시도해 봤지만 내부 자원으로 우회되는 경로는 찾지 못했다.

> **확인** 대부분은 프레임워크 기본 동작으로 막혀 있었다. 다만 "막혀 있다"는 것을 직접 시도해서 확인하고 나서야 안심할 수 있었다.

### 4. 버그 진단

기억에 남는 버그는 네 가지다.

- **iOS 가이드 위치 어긋남**: iOS에서만 흰색 가이드가 오른쪽 위에 몰려 그려졌다. 기기 로그를 찍어 보니 ML Kit이 사진의 EXIF 회전을 적용하지 않은 가로 좌표를 돌려주고 있었다. 반면 이미지 크기는 회전을 적용한 세로 값이라, 가로세로가 뒤바뀐 채 정규화되고 있었다. 회전을 적용한 이미지를 PNG로 다시 인코딩해 ML Kit에 넘기는 방식으로 iOS와 Android의 좌표계를 맞췄다.
- **Provider stale**: 화면을 바꿔도 이전 상태가 남아 있어서 갱신 시점을 바로잡았다.
- **IndexedStack 리로드**: 탭을 오갈 때마다 다시 불러오던 문제를 고쳤다.
- **varchar(255) 초과**: 긴 값이 DB 컬럼 길이를 넘어 저장에 실패했다.

## 서버 구성

배포는 AWS로 했다.

- **EC2**: Spring Boot 서버를 systemd 서비스로 띄워서 죽으면 자동으로 재시작된다. Elastic IP를 붙여 주소가 바뀌지 않게 했다.
- **RDS**: VPC 안쪽에서만 접근할 수 있게 두었다. 그래서 개발할 때는 로컬 PostgreSQL로 따로 검증했다.
- **S3**: 업로드한 이미지를 저장한다. 업로드 API를 S3 전용으로 분리하자고 제안했다.
- **환경변수 파일**: 권한을 `chmod 600`으로 제한하고, 노출됐던 키는 로테이션했다.

## 남은 의문

> **남은 의문** 장소와 포토 스팟을 수정·삭제할 때 작성자를 확인하는 접근 제어(IDOR)가 아직 없다. 누가 어떤 권한으로 지울 수 있는지 팀 합의가 필요해서 보류했다. 다음 단계는 등록자 정보를 저장하고 권한을 확인하는 것이다.

이 밖에도 남은 과제가 있다.

- **레이트리밋의 한계**: 호출 제한을 서버 메모리에 저장한다. JWT가 stateless라 로드밸런서를 두고 서버를 늘리기는 쉽지만, 그러면 서버마다 횟수를 따로 세게 된다. 서버를 늘리려면 Redis 같은 공유 저장소가 필요하다.
- **과거 이력 정리**: 키는 폐기했지만, git 이력과 문서에 남은 옛 값을 지우는 작업은 아직 하지 않았다.
- **저작권과 초상권**: 다른 사람이 올린 사진을 가이드로 쓰기 때문에, 신고가 일정 수를 넘으면 자동으로 숨기는 방식을 검토하고 있다.
- **콜드 스타트**: 처음 쓰는 지역에는 가이드 사진이 없다. 초기 사진을 어떻게 채울지가 서비스 과제로 남았다.
